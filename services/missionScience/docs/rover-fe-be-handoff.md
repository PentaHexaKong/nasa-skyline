# Proposed rover scientific contract

## Review status

The inspected frontend has roadmap references for rover reach and no existing RoverFeed schema or consumer. This change proposes request and response version 0.1.0 for team review. Generated declarations live in `frontend/src/lib/roverContract.proposed.ts`. JSON Schemas live in `contracts/proposals/roverRequest.schema.json` and `roverResponse.schema.json`. Existing feed types and routes remain compatible.

## Optional service

Python exposes `POST /v1/reachability-evaluations` on the isolated rover process. Go exposes `POST /api/rover-science/v1/reachability-evaluations`. An unset ROVER_SCIENCE_URL yields an explicit unavailable response. Core service readiness has no rover dependency. The optional process has its own cache, health route and concurrent-request gate.

The stack starts the rover service and points the gateway at it by default.

```powershell
docker compose up -d --build rover-science backend frontend
```

For standalone execution from the mission-science repository, use its configured Python environment.

```powershell
python -m uvicorn skyline_rover_science.api:app --host 127.0.0.1 --port 8016
```

Assets use the existing mission-science asset-root configuration. Optional stationary relay replay uses ROVER_RELAY_COMPARE_URL pointing to the authoritative Go comparison. Request and response limits are 64 KiB and 16 MiB. Go permits 600 s upstream evaluation and nginx permits 610 s. Scientific budget checks remain separate and cooperative.

## Request

Required user assumptions include speedMps and maximumSlopeDeg. The request also carries canonical site, UTC start, durationS, timeStepS, DEM/projection identifiers, gridRadiusCells, gridResolutionM, observerHeightM, waiting and movement/stopping rules, solarDefinition, communicationMode and computational budget. Canonical units are degrees, meters, seconds and fractions. No percentage, hour or power conversion occurs in this contract.

## Response and rendering

Every envelope includes schemaVersion, contractStatus, dataState, scenarioId, request, units, result, provenance and error. A computed result contains grid, timeGrid, directOnly, relayAssisted, difference, visibility and requestedModeState. Scientific source and implementation identities are explicit. Scenario identity covers the complete scenario and sources, so consumers should key saved outputs by scenarioId.

The grid contains frame, projection WKT, affine transform, actual observer coordinates, DEM identity/hash, projected cell dimensions, terrainValidMask and terrainTraversableMask. Points include edge midpoints as well as cells. cellPointIndices maps flattened row-major cells to points. Terrain elevations, grades and invalid reasons remain available for inspection.

Reachability masks and arrival matrices are row-major. reachedAtTimeMask and waitingOpportunityBinMask are time-major with flattened cell columns. The latter excludes the final endpoint. UTC labels are actual SPICE conversions and can differ by submillisecond from a nominal pinned replay request. A requested relay mode can be unsupported while the envelope contains a computed direct baseline. Consumers must inspect requestedModeState and the individual section state before displaying any assisted metric.

| State | Consumer meaning |
| --- | --- |
| computed | Use values with stated assumptions and provenance |
| unsupported | Requested capability is outside verified scope |
| not_computed | Omitted or budget-exhausted calculation |
| unavailable | Missing terrain, assets, service or compatible data |
| failed | Calculation encountered an unexpected failure |

Noncomputed sections carry null arrays. Unknown terrain cells have null reachability. Known cells that were not reached have false reachability with null arrival. Preserve these distinctions when coloring or summarizing a grid. Fractions count discrete reachable time levels and should be labeled accordingly. Geometric communication should carry the existing scientific qualifications.

## Examples and validation

`examples/roverRequest.proposed.json` and `roverResponse.computed.json` are actual CR1 DEM/SPICE examples generated by `scripts/benchmarkRover.py`. Live Go examples and their timing evidence are recorded separately. `scripts/exportRoverSchemas.py` regenerates both schemas and proposed TypeScript declarations. Python, Go and frontend tests verify the proposed envelope and real-data examples. No RoverFeed path has been registered and no frontend scientific evaluator has been added.
